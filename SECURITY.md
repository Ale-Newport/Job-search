# Security and privacy

Meridian is a single-user local application. It binds its API only to loopback and requires a random per-launch bearer token delivered through a scoped Tauri command. Web origins and Host headers are restricted. The desktop CSP permits only local assets and its loopback API. There is no telemetry.

macOS Keychain holds email tokens, IMAP app passwords and provider keys. SQLite contains configuration and references, never authentication secrets. Browser cookies stay in the dedicated profile and are not logged, sent to text models or included in backups. Your Mac account and FileVault protect local candidate/email data at rest; the live SQLite database itself is not encrypted. Backup exports are authenticated-encrypted with AES-GCM and a scrypt-derived key.

Public source fetching validates HTTP(S) destinations and redirects and rejects local/private destinations. Remote HTML and email are parsed as data. They never execute inside the desktop renderer. React escapes displayed strings. No model output becomes JavaScript, a selector, shell command or executable code. Candidate uploads are size-limited, stored using generated names, and parsed without invoking embedded macros.

Each browser action uses an observed element reference and a document identity. Stale, detached, disabled or obstructed targets are rejected. The global pause gate is checked before input. CAPTCHA, MFA, restricted sources and unknown required data require human interaction. Sensitive fields require explicit policy; automatic submission never silently approves legal/demographic answers.

Review approval is bound to the prepared DOM state, candidate evidence, document versions and answers. Submission attempts are recorded before clicking. The same job cannot receive a second application row. A crash or missing success evidence does not permit blind resubmission. Browser/model confidence cannot override these guards.

Gmail/Graph access is read-only; IMAP uses TLS and readonly mailbox selection. No automatic email sending is implemented. OAuth uses PKCE, unpredictable one-use expiring state and Keychain token storage. Provider client registrations and user consent are required. Arbitrary external endpoint configuration can disclose the selected data to that endpoint; choose providers you trust. Laya and Ollama local modes enforce loopback endpoints.

Structured logs omit request bodies and access logs. Credential-like content is redacted. Browser observation history can include submitted candidate information and should be treated as private. Logs are local. Backups exclude session data and secret references; imported integrations reconnect after restore.

Development mode intentionally uses a fixed local test token. It must be explicitly enabled with `MERIDIAN_DEV=1`; production never silently enables it. CI/browser tests use temporary profiles and synthetic recruitment fixtures, never production accounts or job applications.

Report vulnerabilities privately to the repository owner with a minimal reproduction and no live credentials. If a secret was exposed, revoke it at the provider and remove it from Keychain. Deleting the application's data folder removes personal records and browser sessions; remove Keychain entries separately under service `com.meridian.jobagent`.

The packaged PyInstaller sidecar extracts its Python shared libraries at launch. Ad-hoc local signing needs `com.apple.security.cs.disable-library-validation` for these libraries to load; hardened runtime remains enabled. The same entitlement is applied by Tauri to the signed bundle. Distribution builds should review this requirement with a consistent Developer ID signature across the interpreter and native dependencies.

## Worker and outreach boundaries

Worker commands travel over private inherited JSON pipes with a fixed command allowlist. Web pages and model output cannot create worker commands or execute shell code. Each application owns a profile and only explicitly selected, approved immutable documents are uploadable. Required generated documents remain unapproved drafts until reviewed; PDF, DOCX and TXT versions retain evidence and hashes.

Persisted task checkpoints may contain candidate answers and are private local records, not public diagnostics. Routine browser-step diagnostics omit full DOM observations. Checkpoint serialization recursively redacts credential/header/cookie fields and strips authentication parameters and fragments from URLs while retaining job identifiers. Pending submission receipts prevent blind replay after a crash. Restoring a backup is blocked while any child still owns resources, including a parked browser review.

LinkedIn sending has no configured authorised messaging API in this implementation. The application uses an explicit reviewed clipboard/profile handoff and separate manual-send confirmation. It does not scrape private contacts, bypass login/CAPTCHA/MFA, or infer private addresses. Public contact research and user-imported conversations retain their source evidence. Public career entry points are configuration candidates; a configured URL is not advertised as verified availability.

## Browser assistant bridge (Chrome and Safari extension)

The Meridian Assistant extension reaches Meridian through a second listener, separate from the desktop API (design: `docs/EXTENSION_DESIGN.md`; user view: `docs/EXTENSION.md`). The desktop API keeps its per-launch token and is never exposed to the extension.

**Listener and request policy.** The sidecar binds `127.0.0.1` only, on the first free port of 47615 to 47624, with its own FastAPI app, no access log and `Cache-Control: no-store`. Every request must carry `Host` `127.0.0.1` or `localhost` (DNS-rebinding defence). If an `Origin` is present it must be `chrome-extension://<id>` or `safari-web-extension://<id>`; any other origin, including every web page, gets 403 `origin` (no CORS headers are issued for it, and a preflight is refused). Every mutating request must carry an extension `Origin`; a request without `Origin` is accepted only as GET and still needs a credential, except `hello`. Bodies must be JSON of at most 1 MiB, requests have a 30 s deadline (a long poll waits at most 25 s), at most 64 concurrent requests are served, a connection must deliver a complete request head (request line and headers) within 10 seconds or it is closed, at most 16 such unfinished connections are held per peer address (the oldest is closed to make room; every local process is `127.0.0.1`, so this bounds connections that have not yet said what they want, which a real client is for milliseconds, and never affects a long poll once its head arrived), and while a backup restores every endpoint answers 503. The listener stops accepting work before shutdown. A web page can fire a simple GET at it but cannot read the answer and cannot send a header that triggers a preflight.

**Pairing.** A browser connects once. The extension asks to pair and receives a random six-digit code, which it displays. The user types that code into a native macOS dialog opened by Meridian itself (arguments are passed to `osascript` as separate values, so extension-controlled text cannot become AppleScript), or presses Approve in the app after comparing the code; the first decision wins and the other prompt closes. The dialog has no approve-by-default: only the correct code connects, an empty answer is ignored and a third wrong code denies the request. Limits: one pending request per origin, five starts a minute per origin (compared case-insensitively) and twenty overall, eight pending in total, 120 s expiry. The browser kind is derived from the request's `Origin`, never from the body; an extension id other than the pinned Meridian id (or one listed in `MERIDIAN_EXTENSION_IDS`) is displayed as unrecognised, in red, in the dialog and the app. A sidecar restart expires every unfinished pairing and revokes any approved but unclaimed credential.

**Credential.** `mrd1.<client_id>.<secret>` with a 256-bit secret, released once to the polling extension from memory (valid two minutes); only `sha256(secret)` is stored (`extension_clients.token_hash`, unique), verified in constant time, also for unknown clients. A request that carries an `Origin` must match the origin recorded at pairing. Revocation (app, extension, or a restored backup) makes the next request 401 and also stops the hello proof. Credentials idle for a day from the same origin are retired when that origin pairs again. `mrd1.*` strings are redacted from logs. Backups delete paired browsers, pairing records, sessions and the audit tables, so every browser pairs again after a restore. In the browser, Chrome keeps the credential in extension storage that content scripts cannot read; where that is unavailable (Safari, whose worker cannot complete IndexedDB transactions) it is held in `storage.session` for the browser session only, unreadable by content scripts; an engine that can run the AES-GCM vault with a non-extractable key uses it.

**Anti port-squatting.** After pairing, the worker never sends the credential on trust. Before every credentialed request it calls `GET /v1/hello?client=<id>&nonce=<random>`; the real Meridian answers with `HMAC-SHA256(key = sha256(secret), "meridian-bridge-v1|" + nonce + "|" + port)`, which only a holder of the stored hash can compute and which also binds the answer to the port that served it. A listener that cannot prove it holds the key receives nothing (`proof_failed`). If more than one program on the ports answers like Meridian, the extension refuses to choose and sends nothing to either. Unknown clients get no proof. A client that was revoked gets a different statement that only it can verify, `revoked: true` plus `revoked_proof = HMAC-SHA256(key, "meridian-bridge-v1-revoked|" + nonce + "|" + port)`, so that "revoked" is something Meridian proves and never something the extension infers from silence. **A browser that holds a credential and meets a listener that gives no proof of either kind (`unknown_listener`) does not call that a revocation and does not pair with it on its own**: the options page explains, and pairing needs an explicit confirmation there (a page script cannot give it). Even after the user confirms, the credential that was stored is kept as a fallback (not overwritten) and is restored as soon as the app that issued it answers with its proof, which also drops the credential the unproven listener handed out; a fallback the real app reports revoked, or that is not seen for a month, is dropped.

**What the bridge receives and keeps.** The page sends the scanner's descriptors of each control (label, type, options, whether it has a value) and a bounded page report (URL, title, structured job data, employer description text, up to 80 links). Typed text is never sent, except as `final_value` on an explicit save the user confirmed; password, hidden, file and one-time-code, card, bank, ID-number and security-answer fields are not scanned or saved. Page URLs lose fragments and any query parameter that looks like a credential, a name or an email before they are stored or sent to a model. Field-level audit events hold no values and are pruned after 90 days. Employer text (labels, descriptions, fetched pages) is untrusted data end to end: it is never rendered as HTML (the visual layer uses text nodes in a closed shadow root), never interpreted as instructions (`trusted_as_instructions: false`, injection patterns filtered), and values are inserted only through the page's native setters.

**Research and SSRF controls.** Only Meridian, never the extension, fetches public pages. `fetch_public` allows `http` on port 80 and `https` on 443 only, refuses `.local`, `.internal` and similar names, resolves the host and requires **every** address to be public, connects to the resolved address with the original `Host` and SNI (no rebinding window), re-validates each redirect (at most five), sends no cookies, credentials or proxy settings, accepts text types only, and bounds time (8 s a request) and decompressed size. A candidate site named by a page must be plain `https`. A company website is used as context only after a homepage fetch verified it belongs to the company; `robots.txt` is honoured; LinkedIn, Indeed, Glassdoor, registries and ATS-vendor domains are never treated as the company's own site; page parsing is budgeted and runs off the event loop. The optional last-resort web lookup sends only the company name; it is a setting, and is off in tests. Under `MERIDIAN_TEST` no network research happens unless a test explicitly allows a loopback fixture.

**Answer gate (fail closed).** The assistant offers an answer only when it can be traced to verified facts, a labelled derivation or a validated draft. A factual question is answered only when the whole question is accounted for by a plain canonical form of its family (`intelligence/plain.py`): any extra clause leaves it to the user instead of guessing. Consent and legal confirmations, optional personal-disclosure questions, anything unknown and any answer whose option cannot be mapped are never inserted; protected answers (work authorisation, sponsorship, demographics, a typed signature and similar) are inserted only by an explicit Enter or click unless the user changes the setting (a signature never takes Tab). A field that already holds a different value is never overwritten, a field a person cannot see is not an assist field, a field covered by a layer of the page at the moment of writing is not written (documented gaps: a cover painted only with a shadow, mask or blend mode is not detected, and a covered control below the fold is accepted until it is scrolled to), and the assistant never submits or navigates. Drafts are validated against cited facts, labelled, withdrawn when a cited fact changes, limited per page, browser and hour and by a spending cap, and never written for sensitive, legal or salary questions.

**What is not protected.**

- Any process running as your macOS user can connect to the loopback ports, read Meridian's database and documents, and read browser extension storage. The database is not encrypted at rest.
- Once the user confirms pairing with a listener nobody could vouch for (`unknown_listener`, for example after reinstalling Meridian), that listener is in the same position as at the first pairing: it receives the new credential and, behind its proof, requests made with it, until the original Meridian answers again. The confirmation is the user's call, and the previous credential is not lost meanwhile.
- The first pairing has no shared secret to prove the listener is Meridian. The defence is that the user types a code into a window Meridian must open; a perfect imitation of Meridian that also opens a convincing window is out of scope. The proof also leaves a window of milliseconds between the proof and the request that follows it on a separate connection.
- Traffic on the loopback ports is plain HTTP; it is protected by the loopback boundary and the credential, not by TLS.
- Once the assistant writes a value into a form field, that page's scripts, and the employer after submission, can read it. Insert only on pages you trust with that answer.
- Prompt-injection filtering of employer text is a mitigation, not a proof; a draft is a model output that you must review.
- Any web page can fire the `meridian://open` address, which only raises the Meridian window; nothing in the address is acted on.
- Safari's extension runs under Safari's own rules; behaviour there is not covered by an automated test (see `docs/EXTENSION.md`).
