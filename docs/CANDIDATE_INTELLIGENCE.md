# Candidate Intelligence

The structured model is additive to the existing CV vault and answer history. Migration `0007_candidate_intelligence` creates typed facts (backed by the existing historical fact IDs), entities, evidence relationships, scoped policies and answer provenance. Personal seed data and real-form evidence remain in `.local-data/`, outside Git.

`CandidateEngine.answer_question(question, form_context, job_context)` performs deterministic interpretation and derivation. Its asynchronous `answer` method also uses the configured local Ollama model to interpret unknown concepts or refine an unmappable enum within the same concept. The classifier sees the question and field constraints, not candidate facts. It returns a constrained concept/selector; code selects facts, computes dates/numbers and formats the answer. An existing grounded answer and a known missing fact cannot be replaced by a model classification. Classified answers remain marked for review. Classification errors and provider failures cannot create candidate facts.

The engine separates completed education from ongoing study, contractual notice from academic availability, present salary from expectations, and immigration-route descriptions from permission to work. Dated skill evidence is unioned rather than summed across overlapping projects; professional, academic and project exposure remain separate. Month-only historical dates retain their precision. A missing contract does not prove zero notice.

A narrowly worded temporary UK visa choice can be derived only from both verified current UK work permission and the verified UK Student route. The route alone cannot establish permission, and this derivation does not answer expiry, working hours, unrestricted/full-time permission, future permission or another country's authorization.

New typed identity data supersedes older CV values. Explicit Profile edits create authoritative versions; a draft/clear blocks reuse of the previous value. Equal-priority contradictory evidence produces an unknown answer. Lower-priority conflicting sources remain visible in Knowledge. The established Application profile reads typed person values directly; its generic facts table and patch endpoint cannot corrupt typed JSON. Scoped answers explicitly confirmed in the browser can fill a genuinely missing fact, but cannot revive cleared typed values or bypass an institution conflict. The review fingerprint includes all knowledge, policies and the London calendar date; changing any of those invalidates prior review. Derived values are evaluated anew rather than stored as primary relative facts.

Automatic form narratives use the independent `ApplicationAnswerLLM`. Deterministic `answer_question` resolves factual concepts; asynchronous `answer` routes motivations, technical challenges, behavioral stories, preferences and unusual prose to a configured generative provider. There is no extractive narrative fallback in production. The older composer remains an explicit utility for selected document drafts and diagnostic tests.

Each immutable narrative request contains the complete observed question, its instructions and field constraints, relevant verified facts, professional interests, the actual job description, and public company evidence. Not-on-resume requests additionally include professional text from the exact linked approved CV version; other narratives use retrieved verified professional facts. Website content is data, never instructions. Candidate history and employer requirements remain separate. Output requires a question ID, intent, fact citations, selected options/roles, supported company claims and quality metadata. A provider response alone is not an accepted answer: deterministic format/evidence checks, an independent model review and bounded regeneration run before insertion. Validator failures and measured length corrections become system-level regeneration instructions. Historical implementation methods in the prose are checked even when omitted from the model’s claim index. The source index prioritizes documented technical tradeoffs in a large profile. Exact sourced employer clauses can establish employer dates and programme lengths, but cannot support candidate accomplishments or education metrics. Reference links in a narrative do not impose a URL output format. Missing historical incidents, private preferences and consents remain unknown. Provider/setup failures retain a precise error and never create a template answer.

Settings → AI & providers and Profile → Candidate Intelligence expose answer-provider configuration, discovered models, secure key onboarding, connection tests, usage limits and per-question diagnostics. Credentials remain in macOS Keychain. OpenAI, Anthropic, Gemini, Ollama and configurable compatible endpoints are supported; available models are discovered instead of being fixed in code. The connection probe uses synthetic candidate data. A connection-test success does not certify application-answer quality.

The saved “Use complete professional profile” option includes every current verified professional fact, ordered by question relevance, and the professional text of the linked CV when available. It excludes contact, demographic, legal and credential data, resolves superseded imports, and fails explicitly instead of silently truncating a profile above 250,000 characters. Explicit complete mode permits a 1 MiB generation/review request; ordinary retrieval remains limited to 65,000 bytes. Both transport boundaries are checked before credential access. The ordinary mode retains bounded question retrieval. The provider receives this context on each request; this does not train the model or establish persistent provider memory.

Cloud generation and connection tests require a positive authorized monthly cap and current rates bound to the exact primary or fallback model. A zero cap disables remote inference. Calibration copies use the shared live usage ledger and copy only nonsecret configuration; they cannot reset aggregate spending. Local loopback inference remains available with zero prices and a zero cap.

Native OpenAI settings require ordinary input, cached input, cache-write and output prices for each model. Reservations cover the highest input rate; reported cached/write tokens are settled as subsets of input, and missing usage retains its reservation. Professional previous-answer context includes only validated narrative rows and omits arbitrary metadata, contacts, demographic data and legal/consent answers before every generation, review or regeneration request.

The final form review recomputes supported factual answers against observed controls and scoped knowledge. Unsupported or contradictory populated factual fields require human review. Professional explanations are reviewed as narratives. Typed custom-dropdown search text is excluded until an actual selection is observed; an unresolved dropdown remains a review item while unrelated later fields continue.

Dynamic menus are read before filtering. Closed custom widgets with an independently observed selected label supply that label as an enum contract for factual re-evaluation; the selection itself does not prove the answer. The runner and final factual review share this contract, avoiding repeated selection after a menu disappears. Geocoders retain verified city and country disambiguation even when the closed widget exposes only its selected label.

Native preparation permits a healthy multi-question workflow for up to 30 minutes while retaining per-request timeouts and heartbeat/progress watchdogs. Each question reports generation, regeneration, independent validation and retry progress. Resuming a fill uses the overall preparation timeout instead of treating the idle-progress interval as a workflow timeout. A successful dashboard launch or fixture test does not establish a complete genuine native preparation run.

The explicit `personal_disclosures=leave_blank` policy overrides older demographic preferences and saved answers. It applies to personal gender, pronouns, orientation, ethnicity, religion, health, disability and related disclosures, including optional adjustments and conditional details. The runner clears observed previous values where the control supports clearing, then re-observes. It never substitutes a decline option for blank. An employer-required disclosure stays blank and blocks automatic completion; a control that cannot reliably be cleared requires manual removal. Company diversity text and professional work in related domains are not candidate disclosure questions. The policy remains editable in Knowledge.

The alternative `personal_disclosures=use_confirmed` policy uses explicitly verified Profile facts for each distinct attribute. Gender, sex, pronouns, mental health, neurodivergence, disability and interview adjustments remain separate; a value for one does not establish another. Question-specific option aliases preserve meaning, and native radio groups use the same option resolver as select controls. Missing optional attributes stay blank; required unknown attributes, unsupported existing answers and unavailable matching choices require browser-local review. AI drafting is disabled for personal disclosures. Editing or clearing a profile fact invalidates dependent answers and prevents stale memories from restoring it. The policy can be switched in Knowledge without discarding the stored profile values.

Current attributes cannot answer historical or broader health questions. Browser memories include the personal question's context, so a repeated generic label cannot transfer an answer between unrelated attributes. The observed combobox or an explicitly linked menu toggle is opened before searching; this exposes equivalent options whose labels differ from the profile value. A linked toggle must belong to the same observed widget and cannot be an explicit or implicit form-submit control. Section consent previews the same operation that the filler executes.

Profile → Knowledge exposes facts, evidence, linked entities, policies, conflicts, derivations and a question probe. Settings → Candidate Intelligence shows coverage over an explicit diagnostic question set. Percentages describe that denominator; they are not claims of universal ATS/question coverage. Existing document text can produce unverified CV and labelled immigration proposals. GitHub observations retain source URLs and blob hashes, without converting repository creation times into employment or experience dates.

## Calibration

`scripts/calibrate_intelligence.py` defaults to inspection only and requires a separate database. For genuine narrative form calibration, use `scripts/regress_application_answers.py` with an explicit copied database, output directory and destination URL. `scripts/calibrate_answer_llm.py` runs the ten narrative scenarios against a real configured provider without opening an employer form. Optional repeated `--question` numbers replay specific original scenarios without renumbering their question IDs. It requires the exact `--job` ID and records the selected job ID and URLs; title-based latest-job selection is prohibited. The trusted signed backend exposes the same modules through `--meridian-calibration answers|form`, preserving existing Keychain access without credential export. Personal reports belong in ignored `.local-data/`. `--fill` is a separately authorized operation that uses the normal browser filler in Review mode. Its browser class rejects every submission attempt. No bypass is provided for CAPTCHA, MFA or access restrictions.

Remote calibration also requires `--allow-remote` and `--usage-database` pointing at the existing live database for current model configuration and shared usage accounting. Missing-input narrative cases are reported separately from factual rejection and provider failures. The [October answering overhaul report](ANSWER_OVERHAUL.md) records its distinct factual, narrative and real-form evidence and outstanding checks.

The 3 October 2026 discovery run processed 1,532 postings across 11 configured public sources and selected the actual top ten recommendations. After destination-specific user authorization, these ten applications were exercised with the real candidate profile and approved CV, repeatedly correcting general failures and stopping before submission. The audit compares final observed control values against grounded answers; an attempted write is not counted as a verified answer.

Seven application forms were accessible: Trainline, Mytos, Shift Technology, two Blenheim Chalcot roles, Fifty One Degrees and Elwood. Haleon and British Council remain manual handoffs on Indeed (additional verification/sign-in also appeared during runs). BlackRock's Workday listing linked to an application page which did not expose a usable form. These three paths are not counted as completed forms.

Calibration fixes cover React Select's pointer-open behavior, hidden selected controls and country flags, dial-code decoration, Select2 tree options, geocoder disambiguation by verified city and country, clipped upload controls, dependent questions and asynchronous re-rendering. Dropdown and attachment proxies are validated against their observed DOM relationship. The runner verifies selected values and does not mark its own pre-write state as completed. Employer-populated values without supporting evidence are flagged for review. An application-entry URL can be opened by GET without clicking its possible submission handler; a page containing candidate inputs retains the submission boundary.

An in-progress qualification is explained truthfully when a free-text field presupposes graduation at the latest university. A recent-graduate inference uses a conservative completed-within-twelve-months interpretation, explicitly marked for review because the employer's recency definition is unknown. It does not assert programme eligibility. No ongoing master's is treated as a completed qualification.

The private audit, snapshots and screenshots are under `.local-data/intelligence-release/`. `docs/VERIFICATION.md` records the final counts and remaining restrictions. This is bounded evidence from ten selected destinations, not a guarantee of universal ATS coverage. Missing notice, employer-specific pay/office preferences, exact immigration evidence and separate legal consent remain unresolved without inventing answers.

## Immigration evidence

The user confirmed the Student route; an exact permission expiry, working conditions and future route were not supplied. These are distinct from general study dates. No legal eligibility is invented from Spanish nationality, a CAS or an expected completion date. Reference rules checked on 3 October 2026: [Appendix Student](https://www.gov.uk/guidance/immigration-rules/immigration-rules-appendix-student), [Graduate route](https://www.gov.uk/graduate-visa/overview). The application does not promise a future immigration outcome.

## Context and privacy regression release — 4 October 2026

A stored job description was omitted from the application query, and generic additional-context labels were classified as project requests before their descriptions were considered. Both paths are corrected. Employer context can also come from matching observed job sections or a bounded public refresh when stored text is missing or stale. Form values, applicant answer widgets and validation errors are excluded from employer context.

The regression suite includes paraphrases, weak labels with substantive descriptions, compound questions, purpose-specific prose, distinct roles at the same company, selected-evidence cover letters, policy precedence over stored answers, and browser clearing controls. The authorized Trainline fill-only replay uses a separate database and independently compares final observed values; private evidence is in `.local-data/context-quality/`. No application is submitted. See `VERIFICATION.md` and the release manifest for final counts.
